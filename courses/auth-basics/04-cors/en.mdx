## The problem

Your React app on `https://app.example.com` calls your API on `https://api.example.com`. It worked on `localhost`. In production the browser console shows:

```text
Access to fetch at 'https://api.example.com/me' from origin 'https://app.example.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
```

The same request works in Postman and with `curl`. A teammate suggests `Access-Control-Allow-Origin: *`.

## The idea

An **origin** is the scheme, host and port of a page: `https://app.example.com` and `https://api.example.com` are **different** origins.

Browsers follow the **same-origin policy**: a page's JavaScript may send a request to another origin, but it may **not read the response** unless that server says it is allowed. Otherwise any website you visit could read your email or bank data from other sites, using your cookies.

**CORS** (Cross-Origin Resource Sharing) is how the server gives that permission, with response headers:

- `Access-Control-Allow-Origin: https://app.example.com`: this origin may read the response.
- `Access-Control-Allow-Credentials: true`: the request may include cookies.

For some requests, such as those with JSON bodies or custom headers, the browser first sends a **preflight**: an `OPTIONS` request asking "may I?". The actual request is only sent if the preflight's answer allows it.

That is why Postman works: CORS is enforced **by browsers**, to protect users. It is not a firewall for your API.

`*` means "any website may read this". It is fine for public data, but it can't be combined with cookies, and allowing any origin together with credentials would let every site act as your logged-in users.

## Example

Allow a specific list of origins, with cookies, using the `cors` package:

```ts
import cors from 'cors';

const ALLOWED = new Set(['https://app.example.com', 'https://admin.example.com']);

app.use(
  cors({
    origin: (origin, done) => done(null, !origin || ALLOWED.has(origin)), // !origin: same-origin, curl, server-to-server
    credentials: true, // allow cookies
    methods: ['GET', 'POST', 'PUT', 'DELETE'],
    maxAge: 600 // browsers may cache the preflight answer for 10 minutes
  })
);
```

The browser now receives `Access-Control-Allow-Origin: https://app.example.com` and `Access-Control-Allow-Credentials: true`, and the app can read `/me`. A page on any other website still can't.

On the frontend, include cookies explicitly: `fetch(url, { credentials: 'include' })`.

<Tip title="Or avoid cross-origin calls entirely">
If you serve the app and the API from the same origin, for example `example.com` and `example.com/api` behind one proxy, there is no CORS to configure at all.
</Tip>

## Try it

1. Open the Network tab, trigger a cross-origin call, and find the `OPTIONS` preflight request if there is one.
2. Look at the response headers: which `Access-Control-Allow-*` headers are present?
3. Check your API's CORS settings. Is the origin list exact, or does it echo back **any** origin?
4. If you use cookies, make sure credentials are only allowed for your own origins.

## Check yourself

**1. The request succeeds with `curl` but fails in the browser. Is the server broken?**

<Answer>
Usually not. The server answered, but the browser won't let the page read the response because the CORS headers don't allow its origin. `curl` doesn't enforce CORS.
</Answer>

**2. Why is reflecting any `Origin` header back, together with `Allow-Credentials: true`, dangerous?**

<Answer>
It lets any website make requests with the user's cookies and read the answers. A malicious page could fetch the user's private data from your API while they are logged in.
</Answer>

**3. Why does a `POST` with a JSON body cause an extra `OPTIONS` request?**

<Answer>
`Content-Type: application/json` makes it a "non-simple" request, so the browser sends a preflight first to ask whether the method and headers are allowed. `maxAge` lets the browser cache that answer.
</Answer>

## Key takeaways

- The **browser** enforces CORS, to protect users; Postman and `curl` don't.
- The server grants access with **`Access-Control-Allow-*` headers**.
- List **exact origins**; never combine "any origin" with credentials.
- Serving the app and the API from **one origin** avoids CORS altogether.
