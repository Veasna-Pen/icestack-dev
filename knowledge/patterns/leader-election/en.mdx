## Context

To achieve high availability and zero downtime, services are deployed as multiple identical replicas (e.g., 3 to 10 pods behind a Kubernetes Service).

However, certain tasks in distributed software are inherently **singletons**:
- Scheduling and dispatching recurring cron jobs.
- Rebalancing partition assignments across Kafka consumers.
- Managing cluster membership and state machine coordination.
- Monitoring batch worker progress and issuing heartbeats.

If all 5 pods attempt to run the scheduler, duplicate jobs run. If you deploy only 1 pod to avoid duplicates, that pod becomes a single point of failure (SPOF): if it crashes or restarts, the scheduler dies completely.

The **Leader Election Pattern** reconciles this dilemma. All nodes participate in an election protocol. Exactly one node wins leadership and runs the singleton coordinator tasks. The remaining follower nodes stand by as hot spares, continuously monitoring the leader's lease. If the leader crashes, a follower is promoted to leader within seconds.

## Symptoms

- A single scheduler container is deployed as `replicas: 1` in Kubernetes to prevent duplicate cron executions, but every node upgrade causes 10 minutes of missed billing jobs.
- Multiple worker pods simultaneously trigger cluster rebalances or polling loops, thrashing database connections and corrupting state.
- During deployments, old and new scheduler pods run concurrently for 30 seconds, firing duplicate payroll or subscription renewals.
- A failed leader leaves cluster coordination frozen because followers have no automated way to detect node death and elect a replacement.

<Callout type="warning" title="Leader election requires continuous heartbeating">
A leader does not hold office forever. It must continuously renew a time-limited lease. If network latency or garbage collection pauses prevent renewal, the lease expires and followers elect a new leader.
</Callout>

## Diagnose

1. **Audit singleton workloads:** Which tasks in your system require strictly single-instance execution?
2. **Review deployment replica counts:** Do you have deployments with `replicas: 1` out of fear of duplicate processing?
3. **Inspect failover downtime:** When a scheduler pod restarts, how long does the system remain unmonitored before the new pod boots and takes over?
4. **Evaluate split-brain risk:** If a temporary network partition occurs, could two nodes both believe they are the leader simultaneously?

## Options

1. **Kubernetes Lease API (`coordination.k8s.io/v1`):** Native Kubernetes resource used by controller-managers. Pods acquire and renew leases via Kubernetes API server without extra infrastructure.
2. **Redis-based Leader Election:** Nodes compete for a shared Redis key with `SET leader_key node_id NX PX 5000`. The leader periodically extends the lease via heartbeats. (Fast, lightweight, sub-second failover).
3. **Distributed Consensus Systems (etcd, Consul, ZooKeeper):** Strong CP consensus using Raft or Paxos with ephemeral keys and session heartbeats. (Gold standard for zero split-brain guarantees).
4. **Database row lease (PostgreSQL):** A `leader_leases` table with `UPDATE leader_leases SET owner = 'node-1', expires_at = NOW() + INTERVAL '10s' WHERE expires_at < NOW()`.

## Trade-offs

| Strategy | Failover Latency | Split-Brain Safety | Operational Overhead | Best Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **Kubernetes Lease** | 5–15 seconds | Very High (etcd backed) | Zero (native to K8s) | Kubernetes controllers, operators |
| **Redis Lease** | 1–3 seconds | Moderate (failover edges) | Lowest (if Redis exists) | Web backend cron coordinators |
| **etcd / Consul** | 1–2 seconds | Maximum (Raft consensus) | High (dedicated cluster) | Distributed databases, service mesh |
| **PostgreSQL Lease** | 3–10 seconds | High (ACID) | Zero (uses existing DB) | Monoliths running on relational DBs |

## Decision

- **Use Kubernetes Lease API for containerized infrastructure inside K8s:** If your application runs on Kubernetes, use the native `Lease` object. It requires no Redis or database and is maintained by the Kubernetes control plane.
- **Use Redis Leases with heartbeats for general backend applications:** If running standard Node.js or Go services, acquire leadership with `SET NX PX` and run a background timer renewing the lease every TTL / 3 seconds.
- **Always implement a resignation handler:** When a leader pod receives `SIGTERM` or `SIGINT`, it must immediately delete its lease key so followers can claim leadership instantly in < 100 ms rather than waiting for the lease TTL to expire.
- **Guard against split-brain with Fencing Tokens:** Generate an incrementing epoch counter every time a new leader takes office. Downstream databases and storage systems must reject commands from older leaders bearing stale epoch tokens.

## Implementation

### Production-Grade Redis Leader Election Coordinator in TypeScript:

```typescript
import { Redis } from 'ioredis';
import { randomUUID } from 'crypto';

export class LeaderElection {
  private readonly nodeId = `${process.env.HOSTNAME || 'node'}-${randomUUID().substring(0, 8)}`;
  private isLeader = false;
  private heartbeatTimer: NodeJS.Timeout | null = null;
  private electionTimer: NodeJS.Timeout | null = null;

  constructor(
    private readonly redis: Redis,
    private readonly leaseKey: string,
    private readonly leaseTtlMs = 6000 // 6-second lease
  ) {}

  start(onElected: () => void, onDemoted: () => void) {
    // Attempt election every 2 seconds
    this.electionTimer = setInterval(async () => {
      await this.tryAcquireOrRenew(onElected, onDemoted);
    }, 2000);

    // Initial check
    this.tryAcquireOrRenew(onElected, onDemoted);
  }

  private async tryAcquireOrRenew(onElected: () => void, onDemoted: () => void) {
    try {
      if (this.isLeader) {
        // As leader, renew the lease using atomic Lua script
        const renewScript = `
          if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("pexpire", KEYS[1], ARGV[2])
          else
            return 0
          end
        `;
        const renewed = await this.redis.eval(renewScript, 1, this.leaseKey, this.nodeId, this.leaseTtlMs);
        if (renewed !== 1) {
          // Lost leadership due to missed heartbeat!
          console.warn(`[LeaderElection:${this.nodeId}] Lost leadership! Transitioning to follower.`);
          this.isLeader = false;
          onDemoted();
        }
      } else {
        // As follower, attempt to claim vacant lease
        const acquired = await this.redis.set(this.leaseKey, this.nodeId, 'PX', this.leaseTtlMs, 'NX');
        if (acquired === 'OK') {
          console.log(`[LeaderElection:${this.nodeId}] WON ELECTION! Promoting to LEADER.`);
          this.isLeader = true;
          onElected();
        }
      }
    } catch (err) {
      console.error(`[LeaderElection:${this.nodeId}] Election loop error:`, (err as Error).message);
    }
  }

  async stop(onDemoted: () => void) {
    if (this.electionTimer) clearInterval(this.electionTimer);
    if (this.heartbeatTimer) clearInterval(this.heartbeatTimer);

    if (this.isLeader) {
      // Gracefully resign leadership immediately on shutdown
      console.log(`[LeaderElection:${this.nodeId}] Gracefully resigning leadership...`);
      const resignScript = `
        if redis.call("get", KEYS[1]) == ARGV[1] then
          return redis.call("del", KEYS[1])
        else
          return 0
        end
      `;
      await this.redis.eval(resignScript, 1, this.leaseKey, this.nodeId);
      this.isLeader = false;
      onDemoted();
    }
  }

  checkIsLeader(): boolean {
    return this.isLeader;
  }
}
```

### Usage for a central cluster cron coordinator:

```typescript
const election = new LeaderElection(new Redis(process.env.REDIS_URL!), 'cluster:cron:leader', 6000);

let cronJobHandle: any = null;

election.start(
  // onElected
  () => {
    console.log('This instance is now the ACTIVE LEADER. Starting cron dispatcher...');
    cronJobHandle = setInterval(() => {
      console.log('Dispatching scheduled jobs at', new Date().toISOString());
    }, 10000);
  },
  // onDemoted
  () => {
    console.log('This instance is now a FOLLOWER. Stopping cron dispatcher...');
    if (cronJobHandle) {
      clearInterval(cronJobHandle);
      cronJobHandle = null;
    }
  }
);

// Clean resignation on SIGTERM
process.on('SIGTERM', async () => {
  await election.stop(() => {
    if (cronJobHandle) clearInterval(cronJobHandle);
  });
  process.exit(0);
});
```

## Verification

1. **Initial election test:** Start 3 identical nodes. Verify that exactly 1 logs `WON ELECTION` while the other 2 log nothing and remain followers.
2. **Automated failover test:** Send `kill -9` to the active leader process. Verify that within 6 seconds (the lease TTL), one of the remaining 2 followers detects lease expiration, promotes itself to leader, and starts the cron job.
3. **Graceful resignation test:** Send `SIGTERM` to the active leader. Verify that it voluntarily releases the key and the next leader claims the role in **< 500 ms**.
4. **Split-brain network partition test:** Simulate Redis disconnection on the leader. Verify that the old leader demotes itself upon failing the renew heartbeat.

## Why

High availability requires running multiple redundant instances of an application. But coordination requires a single decision-maker.

Without leader election, software teams are trapped between two unacceptable extremes: running a fragile single instance that causes outages during maintenance, or running multiple instances that accidentally double-charge customers or duplicate batch tasks.

The Leader Election pattern gives systems the best of both worlds: active-passive redundancy with fully automated, sub-second failover.

## When Not To Use

- **Stateless HTTP APIs:** Standard web routes (e.g., fetching a user profile or rendering HTML) do not require a leader; all replicas can serve requests concurrently behind a load balancer.
- **Partitioned consumer streams (Kafka):** Kafka consumer groups already handle partition assignment and rebalancing automatically; manual leader election is unnecessary.

## Common Mistakes

- **Long lease TTL without resignation:** Setting a 60-second lease TTL without a `SIGTERM` resignation handler means that every deployment leaves your scheduler completely dead for 60 seconds.
- **Ignoring the demotion callback:** If a leader loses network connectivity to Redis, it must immediately stop its singleton work; continuing to execute after lease loss causes dual-leader split-brain.
- **Heartbeat interval equal to TTL:** If lease TTL is 5 seconds and heartbeat runs every 5 seconds, a single minor network hiccup will drop leadership. Run heartbeats at TTL / 3 (e.g. every 1.5s for a 5s lease).
