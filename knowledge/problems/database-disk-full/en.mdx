## Context

A production PostgreSQL 16 database running on a 200 GB SSD storage volume. The core tables have around 10 million rows, accounting for roughly 25 GB of actual user data.

Over the past two months, without any abnormal increase in user signups or new rows, the database storage usage steadily climbed from 30 GB to 190 GB (95% full). Cloud monitoring triggers high-severity alerts: if disk reaches 100%, PostgreSQL will automatically enter read-only panic mode or crash.

The team's first reaction is to buy more disk space (expanding to 500 GB), but within a few weeks, disk usage climbs right back toward the new limit.

## Symptoms

- Database disk usage increases continuously while `SELECT count(*)` on main tables remains stable.
- Postgres logs begin warning: `PANIC: could not write to file ... No space left on device`.
- Deleting millions of rows using `DELETE FROM orders WHERE created_at < NOW() - INTERVAL '1 year';` **frees zero bytes of disk space** (in fact, it often consumes slightly more disk!).
- Automatic failover or read replicas become disconnected.

<Callout type="warning" title="In PostgreSQL, DELETE does not reclaim disk space">
PostgreSQL uses Multi-Version Concurrency Control (MVCC). A `DELETE` or `UPDATE` does not overwrite the row on disk; it marks the old row as a "dead tuple" so concurrent transactions can still read it. The physical disk space is never returned to the operating system without vacuuming or table rebuilding.
</Callout>

## Diagnose

1. **Find which tables and indexes are consuming disk:**
   ```sql
   SELECT
     relname AS object_name,
     pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
     pg_size_pretty(pg_relation_size(c.oid)) AS table_size,
     pg_size_pretty(pg_total_relation_size(c.oid) - pg_relation_size(c.oid)) AS index_size
   FROM pg_class c
   JOIN pg_namespace n ON n.oid = c.relnamespace
   WHERE n.nspname = 'public' AND c.relkind IN ('r', 'm')
   ORDER BY pg_total_relation_size(c.oid) DESC
   LIMIT 10;
   ```
2. **Check for dead tuple bloat:**
   ```sql
   SELECT
     relname,
     n_live_tup,
     n_dead_tup,
     round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_tuple_pct,
     last_autovacuum
   FROM pg_stat_user_tables
   ORDER BY n_dead_tup DESC
   LIMIT 10;
   ```
   If `n_dead_tup` is in the millions and `dead_tuple_pct` is above 40%, autovacuum is falling behind or blocked.
3. **Check for abandoned replication slots holding WAL:**
   If the `pg_wal` directory is eating 100 GB, an abandoned replication slot is preventing Postgres from recycling WAL files:
   ```sql
   SELECT
     slot_name,
     active,
     pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal_size
   FROM pg_replication_slots;
   ```
4. **Look for long-running open transactions blocking VACUUM:**
   ```sql
   SELECT pid, now() - xact_start AS duration, query 
   FROM pg_stat_activity 
   WHERE (now() - xact_start) > interval '1 hour';
   ```

## Options

1. **Expand cloud volume storage.** Buys time, but does not fix the underlying bloat.
2. **Run `VACUUM FULL`.** Reclaims physical disk space back to the OS. (Takes an **exclusive table lock**, completely blocking all reads and writes until it finishes!).
3. **Use `pg_repack`.** Reorganizes tables and indexes online without exclusive locks.
4. **Tune Autovacuum settings.** Make autovacuum more aggressive so dead tuples are cleaned before tables bloat.
5. **Drop abandoned replication slots.** Immediately frees gigabytes of retained WAL logs.

## Trade-offs

| Solution | Disk Space Reclaimed | Table Locking | Operational Risk |
| :--- | :--- | :--- | :--- |
| **Bigger Disk** | None (masks issue) | None | Zero (until full again) |
| **`VACUUM FULL`** | **100% of bloat** | **Exclusive lock (Downtime)** | High on production |
| **`pg_repack`** | **100% of bloat** | Minimal (no read/write lock) | Requires extension |
| **Drop Inactive Slot** | **Immediate WAL purge** | None | Must verify slot is unneeded |
| **Tune Autovacuum** | Prevents future bloat | None | Slight CPU/IO increase |

## Decision

1. **Immediate Relief (Emergency):**
   - Check `pg_replication_slots`. If an inactive slot has retained 50+ GB of WAL logs, drop it immediately: `SELECT pg_drop_replication_slot('abandoned_slot_name');`.
   - Terminate any transaction that has been running or `idle in transaction` for more than 2 hours, as it prevents autovacuum from cleaning any dead tuples created after it started.
2. **Long-Term Fix (Prevent Bloat):**
   - Rebuild bloated tables online using `pg_repack` or `REINDEX CONCURRENTLY`.
   - Tune autovacuum to run continuously and aggressively on high-write tables.

## Implementation

### 1. Dropping an abandoned replication slot (reclaims WAL disk instantly)

```sql
-- Find the slot retaining gigabytes of WAL:
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots
WHERE active = false;

-- Drop it:
SELECT pg_drop_replication_slot('debezium_old_cdc_slot');
```

### 2. Tuning Autovacuum for high-update tables

By default, autovacuum only triggers when 20% of a table's rows are dead (`autovacuum_vacuum_scale_factor = 0.2`). On a 50-million-row table, that requires **10 million dead rows** before autovacuum even starts!

Configure aggressive thresholds per table:

```sql
-- Trigger autovacuum when 2% of rows (or 10,000 rows) are dead:
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 10000,
  autovacuum_vacuum_cost_limit = 2000
);
```

### 3. Rebuilding Bloated Indexes Concurrently (No Downtime)

Indexes often suffer more bloat than tables:

```sql
-- Rebuild index in the background without locking writes
REINDEX INDEX CONCURRENTLY idx_orders_customer_id;
```

## Verification

1. **Verify disk space drop:** Run `df -h` or check cloud RDS storage metrics. Dropping inactive replication slots will free disk within 60 seconds as PostgreSQL removes obsolete WAL segments.
2. **Dead tuple ratio:** In `pg_stat_user_tables`, confirm `n_dead_tup` remains under 5% of total table rows during peak traffic hours.
3. **Autovacuum execution logs:** Enable `log_autovacuum_min_duration = 5000` to verify autovacuum runs regularly and finishes without warnings.

## Why

PostgreSQL's MVCC architecture guarantees snapshot isolation: a query starting at 10:00 AM must see the table as it existed at 10:00 AM, even if another transaction updates 1 million rows at 10:01 AM.

To enable this, old row versions must be kept on disk. If a single abandoned transaction stays open, or an unvacuumed table accumulates updates, PostgreSQL is legally forbidden from reusing that disk space. Tuning autovacuum ensures dead rows are quickly unlinked and their disk pages marked for reuse.

## When Not To Use

- **Do not run `VACUUM FULL` during peak production hours.** It requires an exclusive table lock that queues every incoming query until your connection pool collapses.

## Common Mistakes

- **Deleting rows and expecting disk to shrink.** In PostgreSQL, normal `VACUUM` marks space as reusable for future `INSERT`s within the same table, but does *not* shrink the file on disk.
- **Forgetting replication slots created by test tools.** Running a test CDC pipeline (like Debezium or Fivetran) and deleting the consumer container without dropping the Postgres replication slot will silently fill your database disk until the database halts.
