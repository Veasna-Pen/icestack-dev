## Context

An application displays a paginated list of 10 million transactions, audit logs, or catalog items. The API implements standard page-based pagination: `GET /api/transactions?page=1&limit=20` translates to `SELECT * FROM transactions ORDER BY created_at DESC LIMIT 20 OFFSET 0`.

Page 1 executes in 2 ms. Page 10 executes in 8 ms.

However, when a web crawler, automated report exporter, or user navigates to Page 5,000 (`OFFSET 100000`), the query takes **3,800 ms**. When a bot crawls Page 25,000 (`OFFSET 500000`), the query takes **18 seconds**, locking CPU and exhausting database connection slots.

## Symptoms

- Query latency degrades linearly with page depth:
  - Page 1 (`OFFSET 0`): 2 ms
  - Page 100 (`OFFSET 2,000`): 45 ms
  - Page 5,000 (`OFFSET 100,000`): 3,800 ms
  - Page 50,000 (`OFFSET 1,000,000`): 35,000 ms (Timeout)
- Database disk read buffers spike as the database engine traverses massive index ranges.
- Users navigating deep search results experience pagination "page jump" drift (duplicate items appear on page 2 because a new item was inserted while they clicked).

<Callout type="warning" title="OFFSET does not skip rows on disk; it reads and throws them away">
When you execute `LIMIT 20 OFFSET 100000`, PostgreSQL does not jump directly to row 100,001. It reads, parses, and traverses all 100,000 previous rows, counts them, discards them, and then returns the next 20.
</Callout>

## Diagnose

Run `EXPLAIN (ANALYZE, BUFFERS)` on a deep pagination query:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM transactions
ORDER BY created_at DESC
LIMIT 20 OFFSET 200000;
```

Look at the execution output:

```text
Limit (actual time=2410.12..2410.15 rows=20 loops=1)
  Buffers: shared hit=42100 read=18400
  ->  Index Scan using idx_trans_created_at on transactions
        (actual time=0.08..2395.10 rows=200020 loops=1)
```

Notice `rows=200020`: The database had to scan and count over **200,000 rows** and touch 60,000 disk pages just to return 20 rows!

## Options

1. **Optimize OFFSET with Deferred Join.** Fetch only the primary keys with `OFFSET`, then `JOIN` back to the main table. (Reduces I/O on table columns, but still scans $N$ index rows).
2. **Hard-cap maximum page depth.** Disallow navigation past page 50 (`if (page > 50) throw BadRequest`). (Common on Google/Amazon search, but breaks data exports and infinite scrolls).
3. **Keyset / Cursor-based Pagination.** Use the value of the last item on the previous page as a filter anchor (`WHERE created_at < $last_seen_created_at LIMIT 20`).

## Trade-offs

| Strategy | Speed at Page 1 | Speed at Page 10,000 | Can Jump to Arbitrary Page? | Resilient to Concurrent Inserts |
| :--- | :--- | :--- | :--- | :--- |
| **OFFSET Pagination** | **2 ms** | **18,000 ms (Crash)** | **Yes** | No (items drift/duplicate) |
| **Deferred Join** | 2 ms | 1,200 ms | Yes | No |
| **Hard Cap (Limit 50)** | 2 ms | N/A (Blocked) | Up to page 50 | No |
| **Keyset (Cursor)** | **2 ms** | **2 ms (Instant!)** | **No (Next/Prev only)** | **Yes (100% stable)** |

## Decision

1. **For mobile feeds, activity logs, and infinite scroll:** Use **Keyset (Cursor) Pagination** exclusively. Query latency will remain under 5 ms whether you are on the 1st page or the 1,000,000th page.
2. **For public web search catalogs:** Combine Keyset pagination with a **hard cap on arbitrary page jumping** (cap UI jump links to 20 pages, and force users to refine search filters rather than paging to row 100,000).

## Implementation

### 1. The Keyset (Cursor) Pagination Query

Index both the sorting column (`created_at`) and the unique tie-breaker (`id`):

```sql
CREATE INDEX idx_transactions_cursor 
ON transactions (created_at DESC, id DESC);
```

Instead of using `OFFSET`, pass the `created_at` and `id` of the last visible item on the client's screen:

```sql
-- Initial page:
SELECT id, amount, created_at
FROM transactions
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Subsequent page (fetching items older than the last item):
SELECT id, amount, created_at
FROM transactions
WHERE (created_at, id) < ($last_seen_created_at, $last_seen_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

### 2. Node.js API implementation with Base64 Cursor:

```typescript
import { pool } from './db';

interface CursorData {
  createdAt: string;
  id: string;
}

export async function getTransactions(cursor?: string, limit = 20) {
  let query = `
    SELECT id, amount_cents, created_at 
    FROM transactions
  `;
  const params: any[] = [];

  if (cursor) {
    // Decode base64 cursor
    const decoded: CursorData = JSON.parse(Buffer.from(cursor, 'base64').toString('utf8'));
    query += ` WHERE (created_at, id) < ($1, $2)`;
    params.push(decoded.createdAt, decoded.id);
  }

  query += ` ORDER BY created_at DESC, id DESC LIMIT $${params.length + 1}`;
  params.push(limit + 1); // Fetch limit + 1 to detect if there is a next page

  const res = await pool.query(query, params);
  const hasNextPage = res.rows.length > limit;
  const items = res.rows.slice(0, limit);

  // Generate next cursor from last item
  let nextCursor: string | null = null;
  if (hasNextPage) {
    const lastItem = items[items.length - 1];
    nextCursor = Buffer.from(
      JSON.stringify({ createdAt: lastItem.created_at, id: lastItem.id })
    ).toString('base64');
  }

  return { items, nextCursor, hasNextPage };
}
```

## Verification

1. **Benchmark depth invariance:** Run two queries: page 1 and page 50,000.
   - Page 1 query: 3 ms.
   - Page 50,000 Keyset query: **3 ms**.
   The execution time remains **constant $O(1)$** regardless of how deep the user paginates.
2. **Zero drift under concurrent writes:** Continuously insert new rows while paging through 5 pages. Verify that no item is duplicated or skipped.

## Why

PostgreSQL B-Tree indexes store values in sorted order. When using `WHERE (created_at, id) < (...)`, the database uses a **direct binary B-Tree lookup ($O(\log N)$)** to seek straight to the matching leaf node and reads the next 20 entries.

With `OFFSET 100000`, the database cannot know where row 100,000 lives without walking through and counting the previous 100,000 index pointers one by one ($O(N)$).

## When Not To Use

- **Small tables (< 500 rows):** For admin lookup tables with only a few dozen entries, `OFFSET` is simple and its overhead is negligible.
- **Random page jumping requirement:** If a business requirement strictly demands jumping directly to Page 437 without visiting page 436, Keyset pagination cannot fulfill it without deferred joins.

## Common Mistakes

- **Forgetting the unique tie-breaker column.** If multiple rows have the exact same `created_at` timestamp, querying `WHERE created_at < $1` will skip all other rows sharing that timestamp! Always combine with the primary key: `(created_at, id) < ($1, $2)`.
- **Calculating `SELECT count(*)` on every page request.** Running an unindexed `count(*)` on a 10-million row table to show "Page 1 of 500,000" takes 5 seconds. Avoid exact total counts on massive tables; show "Next Page" or estimate counts with `pg_class.reltuples`.
