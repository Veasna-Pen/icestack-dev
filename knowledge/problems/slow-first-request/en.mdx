## Context

A containerized backend service running on Kubernetes, AWS ECS, or a serverless platform (AWS Lambda / Google Cloud Run). Under normal operation, API endpoints respond in 30–50 ms.

However, immediately after a new deployment, during horizontal autoscaling, or after an idle period overnight, the very first request takes **2,500 to 4,000 ms**. Subsequent requests are fast again. Users experience noticeable hangs, and automated health checks occasionally time out and restart new containers before they even serve traffic.

## Symptoms

- P99.9 latency graphs show dramatic vertical spikes immediately following CI/CD deployments.
- The first user to click a checkout or search button after an autoscaling event experiences a 3-second spinning wheel.
- Container logs show the process started in 300 ms, but the first HTTP handler execution took 2,800 ms.
- Kubernetes rolling updates trigger temporary 504 Gateway Timeouts on ingress controllers.

<Callout type="warning" title="A fast server start does not mean a warm server">
Printing `"Server listening on port 3000"` means the TCP port is open. It does not mean the database connection is established, TLS certificates are verified, or code paths are optimized by the JIT compiler.
</Callout>

## Diagnose

Break down where the first request's time is actually spent:

```text
Total First Request Time: 3,250 ms
├── DNS Resolution & TCP/TLS Handshake: 120 ms
├── Database Connection Establishment:  1,850 ms  <-- 57% of total time!
│   ├── DNS lookup to database host
│   ├── TCP 3-way handshake
│   ├── TLS handshake & certificate verification
│   └── Database authentication & session initialization
├── JIT bytecode compilation / classloading: 800 ms
└── Actual SQL Query Execution: 480 ms
```

In 90% of non-serverless cases, the culprit is **Lazy Connection Pooling**:
Most database libraries (such as `pg`, `node-postgres`, `HikariCP`, or ORMs like Prisma and Hibernate) do not open database connections when the application boots. They wait until the very first API request calls `db.query()`. The unlucky first user pays the full price of establishing the pool.

## Options

1. **Keep-warm cron ping.** Run a scheduled curl script every 5 minutes to keep containers awake. (Common hack in serverless, but does not help horizontal autoscaling where new cold instances spawn under load).
2. **Eager database connection pre-warming.** Connect to the database and establish minimum idle connections during startup before listening for HTTP traffic.
3. **Pre-warming critical caches.** Load static reference data (feature flags, permissions, lookups) into memory during boot.
4. **Gate with Kubernetes Readiness Probes.** Mark the pod as `Ready` only after the warm-up sequence completes so the load balancer sends no traffic to unready pods.

## Trade-offs

| Approach | Latency Protection | Startup Speed | Implementation Effort |
| :--- | :--- | :--- | :--- |
| **Keep-warm Cron** | Poor (misses new scaled pods) | Fast | Low |
| **Eager Pool Initialization** | **High (eliminates DB delay)** | Adds 1–2s to startup | Low (5 lines of code) |
| **Readiness Probe Gating** | **High (shields users)** | Pod takes longer to become Ready | Minimal config |
| **Ahead-Of-Time (AOT) Build** | Medium (improves JIT) | Fast | High (tooling changes) |

## Decision

1. **Eagerly warm database pools during startup:** Never defer database handshakes to the first user request. Run a simple `SELECT 1` ping during service boot to force the pool to establish initial connections.
2. **Gate traffic with Readiness Probes:** Ensure Kubernetes or your cloud load balancer does not route customer traffic until the eager initialization promise resolves.
3. **Do not rely on keep-warm cron jobs:** They create artificial traffic and fail precisely when autoscaling spins up new replica instances under real spikes.

## Implementation

### 1. Eager connection warmup in Node.js

```typescript
import express from 'express';
import { Pool } from 'pg';

const app = express();
export const pool = new Pool({
  host: process.env.DB_HOST,
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  max: 10,
  min: 2, // Maintain at least 2 warm idle connections
});

let isReady = false;

// Health check endpoint for Kubernetes
app.get('/healthz/ready', (req, res) => {
  if (isReady) {
    return res.status(200).send('READY');
  }
  return res.status(503).send('WARMING_UP');
});

async function startServer() {
  console.log('Pre-warming database connection pool...');
  const start = Date.now();

  try {
    // Eagerly acquire and test connections
    const client = await pool.connect();
    await client.query('SELECT 1');
    client.release();
    console.log(`Database pool warmed in ${Date.now() - start} ms`);

    // Mark service as ready for traffic
    isReady = true;

    app.listen(3000, () => {
      console.log('HTTP server accepting traffic on port 3000');
    });
  } catch (err) {
    console.error('Failed to pre-warm database, aborting startup', err);
    process.exit(1);
  }
}

startServer();
```

### 2. Kubernetes Readiness Probe Configuration

Ensure Kubernetes waits for the warmup to complete before routing traffic:

```yaml
readinessProbe:
  httpGet:
    path: /healthz/ready
    port: 3000
  initialDelaySeconds: 3
  periodSeconds: 2
  failureThreshold: 3
```

## Verification

1. **Measure first-request p99:** Trigger a deployment and immediately execute a curl request against an authenticated endpoint. Latency on request #1 should match request #100 within $\pm 20$ ms.
2. **Zero rolling deploy errors:** Run an automated continuous load test (`k6 run loadtest.js`) while deploying a new release. There should be **zero HTTP 502, 503, or 504 errors** and zero latency spikes during the pod turnover.

## Why

Network protocols require multiple round-trips to establish trust and state before transmitting application payload:
- TCP: 1 round-trip (SYN, SYN-ACK, ACK)
- TLS 1.3: 1 round-trip for cryptographic key exchange
- PostgreSQL: 2–3 round-trips for authentication salt, password verification, and session parameter initialization

If your database is in a different availability zone (1 ms round-trip) or cloud region (30 ms round-trip), connection negotiation alone takes dozens or hundreds of milliseconds. Doing this lazily on the first customer request penalizes users for system operational events.

## When Not To Use

- **CLI tools and short-lived batch scripts:** If a script runs once and terminates in 500 ms, lazy initialization is faster because the script may not even execute all queries.
- **Extreme scale-to-zero serverless functions:** In AWS Lambda with very low traffic where instances are destroyed after every invocation, keep startup code minimal and consider connection proxies like AWS RDS Proxy.

## Common Mistakes

- **Starting the HTTP listener before the database is ready.** If your app listens on port 3000 immediately, the load balancer will route requests before the pool is initialized.
- **Using Readiness probes that do heavy work.** A readiness probe runs every few seconds; it should check a boolean flag `isReady`, not run heavy SQL queries every 5 seconds.
- **Missing DNS caching.** Node.js does not cache DNS resolutions by default. The first request to external APIs often incurs full DNS lookup delays. Use a caching DNS agent or Node.js `dns.setDefaultResultOrder`.
