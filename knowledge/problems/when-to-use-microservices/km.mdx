## Context

ផលិតផលមួយដែលចាប់ផ្តើមជា application តែមួយ (Laravel, Rails, Django, Express ឬ NestJS) ហើយបានរីកធំឡើង។ ការ deploy យឺតជាងមុន កូដពិបាកផ្លាស់ប្តូរជាងមុន ហើយក្រុមបានកើនពីបីនាក់ដល់ដប់ពីរនាក់។ មាននរណាម្នាក់ស្នើឱ្យបំបែកវាទៅជា services៖ users, orders, payments, notifications។

Microservices គឺជា services ដែលអាច deploy ដោយឯករាជ្យ ដែលជាម្ចាស់ទិន្នន័យរបស់ខ្លួន ហើយទំនាក់ទំនងគ្នាតាម network។ អត្ថប្រយោជន៍របស់វាទាក់ទងនឹងការរៀបចំក្រុម ច្រើនដូចបច្ចេកទេសដែរ; ចំណែកការចំណាយរបស់វាភាគច្រើនគឺផ្នែកប្រតិបត្តិការ។

## Symptoms

បញ្ហាដែលជាញឹកញាប់ត្រូវបាន *ចោទប្រកាន់* ថាមកពី monolith៖

- ការផ្លាស់ប្តូរនៅផ្នែកមួយ ធ្វើឱ្យមុខងារដែលមិនពាក់ព័ន្ធខូច។
- Test suite ចំណាយពេល 40 នាទី ដូច្នេះមនុស្សប្រមូលការផ្លាស់ប្តូរជាដុំធំ ហើយការ deploy កាន់តែគួរឱ្យខ្លាច។
- ក្រុមនានារង់ចាំគ្នាទៅវិញទៅមកដើម្បី merge និង release។
- មុខងារធ្ងន់មួយ ដូចជាការបង្កើតរបាយការណ៍ ឬការដំណើរការវីដេអូ ធ្វើឱ្យអ្វីៗផ្សេងទៀតយឺត។
- អ្នកអភិវឌ្ឍថ្មីចំណាយពេលរាប់ខែ ទើបអាចធ្វើការងារបានល្អ។

មានតែមួយចំនួនប៉ុណ្ណោះក្នុងចំណោមបញ្ហាទាំងនេះ ដែលកើតចេញពីការដំណើរការជា deployable តែមួយ។ ភាគច្រើនកើតចេញពីការខ្វះព្រំដែនរវាង modules, tests យឺត និងភាពជាម្ចាស់មិនច្បាស់ ហើយបញ្ហាទាំងនេះនឹងដើរតាមកូដចូលទៅក្នុង microservices ដែរ។

## Diagnose

1. **តើការឈឺចាប់នេះនិយាយពីការ deploy ឬពីកូដ?** ប្រសិនបើ modules ជាប់ជំពាក់គ្នា ការដាក់ network នៅចន្លោះពួកវា ធ្វើឱ្យភាពជាប់ជំពាក់នោះយឺតជាងមុន និងពិបាក debug ជាងមុន។ គូសផែនទី dependencies ជាមុនសិន៖ ផ្នែកណានៃកូដហៅផ្នែកណា ហើយផ្នែកនីមួយៗ write ទៅ tables ណាខ្លះ។
2. **មានក្រុមប៉ុន្មាន ហើយតើពួកគេត្រូវការ ship ដោយឯករាជ្យដែរឬទេ?** ក្រុមតែមួយដែលមានប្រាំមួយនាក់ ទទួលបានផលតិចតួចពីការ deploy ដោយឯករាជ្យ។ ក្រុមបួនដែលរារាំង release របស់គ្នាទៅវិញទៅមក ទទួលបានផលច្រើន។
3. **តើផ្នែកខ្លះត្រូវការ scaling ឬភាពជឿជាក់ខុសគ្នាដែរឬទេ?** Video transcoder ដែលស៊ី CPU ខ្លាំង នៅក្បែរ API ដែលត្រូវការ latency ទាប គឺជាហេតុផលពិតប្រាកដ។ «Orders ប្រហែលជាត្រូវ scale នៅថ្ងៃណាមួយ» មិនមែនជាហេតុផលទេ។
4. **តើអ្នកអាចដំណើរការវាបានដែរឬទេ?** Service នីមួយៗត្រូវការ CI/CD, monitoring, alerting, on-call, logs ដែលមាន correlation IDs និងផែនការសម្រាប់ពេលដែលការហៅរវាង services បរាជ័យ។
5. **តើព្រំដែនទិន្នន័យនៅឯណា?** ប្រសិនបើ «services» ពីរត្រូវ join tables របស់គ្នាទៅវិញទៅមកក្នុង requests ភាគច្រើន នោះវាគឺជា service តែមួយ។

## Options

1. **រក្សា monolith ហើយដោះស្រាយការឈឺចាប់ដោយផ្ទាល់៖** tests លឿនជាងមុន, feature flags, ភាពជាម្ចាស់កូដ (code ownership) និង CI ល្អជាងមុន។
2. **Modular monolith៖** deployable តែមួយ ដែលព្រំដែនរវាង modules ត្រូវបានអនុវត្តយ៉ាងតឹងរ៉ឹង (folder ឬ package មួយសម្រាប់ domain នីមួយៗ មិនលូកដៃចូល tables របស់ module ផ្សេង និង interfaces ច្បាស់លាស់)។
3. **ដកចេញ service តែមួយ** នៅកន្លែងដែលមានហេតុផលជាក់ស្តែង៖ scaling ខុសគ្នា ក្រុមដាច់ដោយឡែក ឬបច្ចេកវិទ្យាខុសគ្នា។
4. **Microservices ពេញលេញ៖** បំបែកតាមសមត្ថភាពអាជីវកម្ម ដែល service នីមួយៗមានទិន្នន័យ និង deploy pipeline ផ្ទាល់ខ្លួន។

## Trade-offs

| | Monolith | Modular monolith | Service ដែលដកចេញមួយ | Microservices |
| :--- | :--- | :--- | :--- | :--- |
| Deploy ដោយឯករាជ្យ | ទេ | ទេ | សម្រាប់ service នោះ | បាន |
| ការអភិវឌ្ឍលើម៉ាស៊ីនផ្ទាល់ | សាមញ្ញ | សាមញ្ញ | ភាគច្រើនសាមញ្ញ | ពិបាក៖ services ច្រើន, fakes |
| ការផ្លាស់ប្តូរឆ្លង domains | PR មួយ | PR មួយ | PR ពីរ និង API ដែលមាន version | PRs ច្រើនដែលត្រូវសម្របសម្រួលគ្នា |
| ចំណុចខូច | ក្នុង process | ក្នុង process | Network, ការខូចមួយផ្នែក | Network គ្រប់ទីកន្លែង, ការខូចរាលដាល |
| ភាពស៊ីសង្វាក់នៃទិន្នន័យ | Transactions | Transactions | Outbox ឬ sagas នៅព្រំដែនមួយ | Sagas និង eventual consistency |
| ការចំណាយប្រតិបត្តិការ | ទាប | ទាប | មធ្យម | ខ្ពស់៖ platform, tracing, on-call សម្រាប់ service នីមួយៗ |
| សមស្របសម្រាប់ | មួយ ឬពីរក្រុម | ពីរដល់ប្រាំមួយក្រុម | គ្រប់ទំហំ សម្រាប់តម្រូវការជាក់លាក់ | ក្រុមច្រើន |

ការចំណាយដែលសម្រេចលទ្ធផល គឺជាការចំណាយដែលមនុស្សប៉ាន់ស្មានតិចជាងការពិត៖ transactions ដែលឥឡូវនេះលាតសន្ធឹងលើ services ច្រើន, ការ debug ឆ្លង network hops និងការងារ platform (deploys, service discovery, tracing) ដែលត្រូវតែមានជាមុន ទើប service ដំបូងអាចមានប្រយោជន៍។

## Decision

**ជ្រើសរើស modular monolith ជាលំនាំដើម។** អនុវត្តព្រំដែនយ៉ាងតឹងរ៉ឹងនៅក្នុង deployable តែមួយ ហើយដកចេញ service លុះត្រាតែ module ជាក់លាក់មួយមានហេតុផលជាក់ស្តែង៖ ក្រុមដែលត្រូវការកាលវិភាគ release ផ្ទាល់ខ្លួន លក្ខណៈ scaling ខុសគ្នា ឬតម្រូវការដាច់ដោយឡែក ដូចជា component ទូទាត់ប្រាក់ដែលស្ថិតក្រោម compliance តឹងរ៉ឹងជាង។

ពិនិត្យឡើងវិញ នៅពេលក្រុមនានានៅតែរារាំង release របស់គ្នាទៅវិញទៅមក ទោះបីជាមានព្រំដែន modules ល្អក៏ដោយ ឬនៅពេល load ឬការខូចរបស់ module មួយប៉ះពាល់ដល់ផ្នែកផ្សេងទៀតម្តងហើយម្តងទៀត។

## Implementation

ធ្វើឱ្យព្រំដែនក្លាយជាការពិតនៅក្នុង monolith ជាមុនសិន។ នៅក្នុង codebase Node.js/TypeScript ផ្តល់ឱ្យ module នីមួយៗនូវ public entry point តែមួយ ហើយហាមឃាត់ការ import ចូលជ្រៅដោយប្រើ lint rule៖

```text
src/
  modules/
    orders/
      index.ts        # the only public surface of the module
      internal/…
    billing/
      index.ts
      internal/…
```

```js
// eslint.config.js: other modules may import 'modules/billing', never its internals
export default [
  {
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [{
          group: ['**/modules/*/internal/**'],
          message: 'Import the module entry point instead.'
        }]
      }]
    }
  }
];
```

Module នីមួយៗជាម្ចាស់ tables របស់ខ្លួន។ Modules ផ្សេងទៀតហៅ functions របស់វា មិនដែលហៅ tables របស់វាដោយផ្ទាល់ទេ។ ប្រសិនបើនៅពេលក្រោយ module មួយត្រូវក្លាយជា service នោះ public interface របស់វាក្លាយជា API ហើយ tables របស់វាផ្លាស់ទីទៅជាមួយ ខណៈដែលកូដដែលនៅសល់ស្ទើរតែមិនផ្លាស់ប្តូរ។

## Verification

- **ការឈឺចាប់ដើមបានប្រសើរឡើង៖** រយៈពេលពីការ merge ដល់ production, ចំនួនជម្លោះ release រវាងក្រុម ឬ incidents ដែលបណ្តាលមកពីការផ្លាស់ប្តូរដែលមិនពាក់ព័ន្ធ។
- **ព្រំដែនរឹងមាំ៖** lint rule មិនមានការបិទ (suppressions) ទេ ហើយគ្មាន module ណា query tables របស់ module ផ្សេង (ស្វែងរកឈ្មោះ table នីមួយៗនៅខាងក្រៅម្ចាស់របស់វា)។
- **សម្រាប់ service ដែលបានដកចេញ៖** វា deploy តាមកាលវិភាគផ្ទាល់ខ្លួន ហើយនៅពេលវាគាំង ប្រព័ន្ធដែលនៅសល់ថយចុះគុណភាព (degrade) ជំនួសឱ្យការបរាជ័យទាំងស្រុង។

## Why

Microservices ដោះដូរភាពស្មុគស្មាញនៅក្នុង process ទៅជាភាពស្មុគស្មាញរវាង processes។ ការដោះដូរនោះផ្តល់ផលចំណេញ នៅពេលស្ថាប័នខ្លួនឯងជាចំណុចកកស្ទះ៖ ក្រុមច្រើន វដ្ត release ឯករាជ្យ និងតម្រូវការប្រតិបត្តិការខុសៗគ្នា។ វាកម្រផ្តល់ផលចំណេញសម្រាប់គុណភាពកូដណាស់ ព្រោះព្រំដែនគឺជាលក្ខណៈនៃការរចនា មិនមែនជាលក្ខណៈនៃការ deploy ទេ។ អ្នកអាចមានព្រំដែនស្អាតនៅក្នុង process តែមួយ ហើយក៏អាចមាន «distributed monolith» ដែលរាលដាលលើ services ម្ភៃដែរ។

## When Not To Use

- **ក្រុមតូចៗ** មួយ ឬពីរក្រុម ឬតិចជាងប្រហែល 15 engineers ដែលគ្មាន platform team។
- **ផលិតផលថ្មីៗ** ដែលព្រំដែន domain នៅតែផ្លាស់ប្តូរ។ ព្រំដែន service ដែលខុស ជួសជុលថ្លៃជាងព្រំដែន module ដែលខុសច្រើនណាស់។
- **ដើម្បីជួសជុល codebase ដែលរញ៉េរញ៉ៃ។** ជួសជុល modules ជាមុនសិន។
- **នៅពេល requests ភាគច្រើនត្រូវការទិន្នន័យពី services ភាគច្រើន** ដែលមានន័យថាព្រំដែនស្ថិតនៅកន្លែងខុស។
- **ដោយគ្មានមូលដ្ឋានគ្រឹះ៖** automated deploys, centralized logs, tracing និង on-call។

## Common Mistakes

- **Distributed monolith៖** services ដែលត្រូវតែ deploy ជាមួយគ្នា ហើយប្រើ database តែមួយរួមគ្នា។
- **បំបែកតាមស្រទាប់បច្ចេកទេស** (API service, database service) ជំនួសឱ្យការបំបែកតាមសមត្ថភាពអាជីវកម្ម។
- **ខ្សែសង្វាក់ការហៅ synchronous** ដែល request របស់អ្នកប្រើម្នាក់ហៅ services ប្រាំតាមលំដាប់។ Availability គុណគ្នាចុះតាមខ្សែសង្វាក់៖ services ប្រាំដែលនីមួយៗមាន 99.9% ផ្តល់ត្រឹមប្រហែល 99.5%។ សូមមើល [Sync vs async](../../tradeoffs/sync-vs-async)។
- **Tables រួមគ្នារវាង services** ដែលធ្វើឱ្យពួកវាជាប់ទាក់ទងគ្នាតឹងជាង monolith ទៅទៀត។
- **ដកចេញលឿនពេក** មុនពេលក្រុមបានរៀនដឹងថាព្រំដែនណាខ្លះស្ថិតស្ថេរ។
- **ភ្លេចទិន្នន័យ។** ការបំបែកកូដគឺងាយស្រួល; ការបំបែក tables ដែលមាន foreign keys រាប់ឆ្នាំ ទើបជាគម្រោងពិតប្រាកដ។
