## Context

ផលិតផលដែលជោគជ័យស្ទើរតែទាំងអស់ ចាប់ផ្តើមជា monolith៖ codebase មួយ deployable មួយ និង database មួយ។ សំណួរដែលមានប្រយោជន៍ មិនមែនថា monoliths ល្អឬអត់នោះទេ។ វាគឺថា នៅពេលណាដែល monolith ជាក់លាក់មួយលែងបម្រើក្រុមបានល្អ ហើយថាតើការបំបែកវានឹងជួយ ឬគ្រាន់តែផ្លាស់ទីការឈឺចាប់ទៅកន្លែងផ្សេង។

ទំព័រនេះប្រៀបធៀបទម្រង់ទាំងពីរដោយផ្ទាល់។ សម្រាប់សំណួរតូចជាងនេះ ថាតើគួរប្រើ microservices ឥឡូវនេះឬអត់ សូមមើល [តើនៅពេលណាដែលខ្ញុំគួរប្រើ microservices?](../../problems/when-to-use-microservices)។

## Symptoms

សញ្ញាដែលបង្ហាញថា monolith កំពុងក្លាយជាបញ្ហា ប្រហែលតាមលំដាប់ដែលវាលេចឡើង៖

- **ការចំណាយលើការសម្របសម្រួល៖** ការ release ត្រូវការកិច្ចប្រជុំ ហើយការងារមិនទាន់ចប់របស់ក្រុមមួយ រារាំងការ deploy របស់ក្រុមមួយទៀត។
- **ការផ្លាស់ប្តូររាលដាល៖** មុខងារតូចមួយប៉ះពាល់ modules ជាច្រើនដែលមិនពាក់ព័ន្ធ។
- **កាំនៃការផ្ទុះ (blast radius)៖** bug ឬ memory leak នៅក្នុងមុខងារមួយ ធ្វើឱ្យមុខងារទាំងអស់គាំង។
- **ជម្លោះធនធាន៖** batch job ឬ endpoint ធ្ងន់មួយ ដណ្តើមធនធានពី requests ដែលត្រូវការ latency ទាប។
- **ពេលវេលា build និង test** ដែលកើនលឿនជាងទំហំ codebase។

អ្វីដែល *មិនមែន* ជាបញ្ហាដោយខ្លួនឯង៖ ចំនួនបន្ទាត់កូដ អាយុរបស់ framework ឬការពិតដែលថាវាជា «monolith»។

## Diagnose

វាស់វែង ជំនួសឱ្យការប្រកែក៖

1. **Lead time សម្រាប់ការផ្លាស់ប្តូរ៖** ពេលវេលាពីការ merge ដល់ production តាមក្រុមនីមួយៗ។ Lead time ដែលកើនឡើង ខណៈទំហំក្រុមនៅថេរ គឺជាសញ្ញាពិតប្រាកដ។
2. **ការជាប់ទាក់ទងនៃការ deploy៖** ញឹកញាប់ប៉ុណ្ណាដែលការ deploy ត្រូវបានរារាំង ឬ rollback ដោយសារការផ្លាស់ប្តូររបស់ក្រុមផ្សេង។
3. **ការជាប់ទាក់ទងនៃការផ្លាស់ប្តូរ៖** ផ្នែកណាខ្លះនៃកូដផ្លាស់ប្តូរជាមួយគ្នានៅក្នុងប្រវត្តិ git។ ឯកសារដែលតែងតែផ្លាស់ប្តូរជាមួយគ្នា គួរស្ថិតនៅក្នុង module តែមួយ; modules ដែលតែងតែផ្លាស់ប្តូរជាមួយគ្នា គួរស្ថិតនៅក្នុង service តែមួយ។
4. **កាំនៃការផ្ទុះរបស់ incidents៖** ក្នុងចំណោម incidents កាលពីត្រីមាសមុន តើមានប៉ុន្មានដែលចាប់ផ្តើមនៅផ្នែកមួយ ហើយធ្វើឱ្យផ្នែកផ្សេងដែលមិនពាក់ព័ន្ធឈឺចាប់។
5. **លក្ខណៈធនធានតាមផ្នែកនីមួយៗ៖** CPU, memory និង latency តាមក្រុម endpoints នីមួយៗ។ តើលក្ខណៈរបស់ផ្នែកមួយពិតជាខុសគ្នាមែនទេ?

ការមើលដំបូងទៅកន្លែងដែលការផ្លាស់ប្តូរប្រមូលផ្តុំ៖

```bash
# Which folders change most often? (last six months)
git log --since="6 months ago" --name-only --pretty=format: \
  | grep '^src/' | cut -d/ -f1-3 | sort | uniq -c | sort -rn | head -20
```

ឧបករណ៍ដូចជា `code-maat` ទៅឆ្ងាយជាងនេះ ហើយគណនាការជាប់ទាក់ទងនៃការផ្លាស់ប្តូររវាងឯកសារ និង folders ពីប្រវត្តិដដែល។

## Options

1. **រក្សា monolith ដដែល** ហើយជួសជុល pipeline និង tests។
2. **Modular monolith៖** ព្រំដែនខាងក្នុងដែលអនុវត្តយ៉ាងតឹងរ៉ឹង ហើយនៅតែជា deployable តែមួយ។
3. **Monolith បូក services មួយចំនួន** ដែលដកចេញដោយប្រើ strangler fig pattern នៅកន្លែងដែលមានតម្រូវការជាក់ស្តែង។
4. **Microservices៖** services ជាច្រើនដែល deploy ដោយឯករាជ្យ ដែលនីមួយៗជាម្ចាស់ទិន្នន័យរបស់ខ្លួន។

## Trade-offs

| វិមាត្រ | Monolith | Modular monolith | Microservices |
| :--- | :--- | :--- | :--- |
| ពេលវេលាដល់មុខងារដំបូង | លឿនបំផុត | លឿន | យឺត៖ platform ត្រូវមកមុន |
| Refactor ឆ្លង domains | ងាយ៖ IDE មួយ PR មួយ | ងាយ ក្នុងក្របខណ្ឌច្បាប់ | ពិបាក៖ APIs, versions, data migrations |
| ស្វ័យភាពរបស់ក្រុម | ទាប | មធ្យម | ខ្ពស់ |
| ឯករាជ្យភាពនៃការ release | គ្មាន | គ្មាន | តាម service នីមួយៗ |
| ការញែកការខូច | គ្មាន | តិចតួច | តាម service ប្រសិនបើរចនាសម្រាប់វា |
| Scaling | App ទាំងមូល | App ទាំងមូល | តាម service នីមួយៗ |
| ភាពស៊ីសង្វាក់ | ACID transactions | ACID transactions | Eventual ជាមួយ sagas និង outboxes |
| Debugging | Stack traces | Stack traces | ត្រូវការ distributed tracing |
| ការចំណាយប្រតិបត្តិការ | ទាប | ទាប | ខ្ពស់ ហើយកើនតាមចំនួន services |
| ទំហំក្រុមធម្មតា | រហូតដល់ប្រហែល 15 engineers | ប្រហែល 10 ដល់ 50 | ក្រុមច្រើន បូក platform team |

ការចំណាយរបស់ microservices ត្រូវបង់ជាមុន និងជាបន្តបន្ទាប់៖ platform, tracing និងការដោះស្រាយការខូចរបស់ network។ អត្ថប្រយោជន៍របស់វាមកដល់ លុះត្រាតែក្រុមជាច្រើនត្រូវការស្វ័យភាព។ ការចំណាយរបស់ monolith កើនយឺតៗ តាមចំនួនក្រុមដែលចែករំលែកវា។

## Decision

- **ក្រោមប្រហែល 15 engineers ឬមុនពេលរកឃើញ product-market fit៖** monolith មួយ ជាមួយ modules សមហេតុផល។
- **នៅពេលចំនួនក្រុមកើនឡើង៖** modular monolith ដែលមានព្រំដែនអនុវត្តយ៉ាងតឹងរ៉ឹង។ វារក្សា transactions និងការ debug សាមញ្ញ ហើយធ្វើឱ្យការដកចេញនៅពេលក្រោយថោក។
- **នៅពេលការវាស់វែងបង្ហាញថា module មួយត្រូវការ releases, scaling ឬការញែកផ្ទាល់ខ្លួន៖** ដក module តែមួយនោះចេញជា service ដោយប្រើ strangler fig pattern។
- **Microservices ពាសពេញ** លុះត្រាតែមានក្រុមច្រើន platform ដែលអាចដំណើរការវាបាន និងព្រំដែនដែលបានបង្ហាញថាស្ថិតស្ថេរ។

Monolith «ក្លាយជាបញ្ហា» នៅចំណុចដែលការចំណាយលើការសម្របសម្រួលក្រុមនៅក្នុងវា លើសពីការចំណាយលើការដំណើរការពួកគេដាច់ដោយឡែក។ ទាំងពីរអាចវាស់វែងបាន។

## Implementation

Strangler fig pattern ដកសមត្ថភាពមួយចេញ ដោយមិនចាំបាច់សរសេរឡើងវិញទាំងស្រុង។ បញ្ជូន paths របស់ service ថ្មីនៅ proxy ហើយផ្លាស់ traffic ទៅវាបន្តិចម្តងៗ៖

```nginx
# Every request still goes to the monolith, except the capability being extracted.
upstream monolith      { server monolith:8080; }
upstream notifications { server notifications:8080; }

server {
  location /api/notifications/ { proxy_pass http://notifications; }
  location /                   { proxy_pass http://monolith; }
}
```

បន្ទាប់មក តាមលំដាប់៖

1. សាងសង់ service ថ្មីនៅពីក្រោយ API contract ដដែល ខណៈដែល writes នៅតែឆ្លងកាត់ monolith។
2. ចម្លង ឬចែករំលែកទិន្នន័យដែលវាត្រូវការ បន្ទាប់មកធ្វើឱ្យ service ក្លាយជាម្ចាស់ tables ទាំងនោះ។ Monolith ហៅ API របស់ service ជំនួសឱ្យ tables។
3. ផ្លាស់ read traffic បន្ទាប់មក write traffic នៅពីក្រោយ flag ដែលអ្នកអាចបិទវិញបាន។
4. លុបផ្លូវកូដចាស់ចេញពី monolith។ ការដកចេញមិនទាន់ចប់ រហូតដល់ជំហាននេះរួចរាល់។

## Verification

- **Metric ដែលជំរុញការបំបែកបានប្រសើរឡើង៖** lead time សម្រាប់ក្រុមដែលជាម្ចាស់ service កាំនៃការផ្ទុះរបស់ incidents ឬការញែកធនធាន។
- **គ្មានអ្វីអាក្រក់ជាងមុនសម្រាប់អ្នកប្រើ៖** latency និង error rates ពីដើមដល់ចប់ សម្រាប់ flows ដែលឥឡូវនេះឆ្លងកាត់ network។
- **ព្រំដែនពិតជាមាន៖** service deploy ដោយខ្លួនឯង ហើយ monolith លែងប៉ះ tables ដែលបានផ្លាស់ទីទៀតហើយ។

## Why

ស្ថាបត្យកម្មដើរតាមការទំនាក់ទំនង។ Monolith មានប្រសិទ្ធភាព ដរាបណាមនុស្សដែលផ្លាស់ប្តូរវាអាចសម្របសម្រួលគ្នាបានដោយថោក ហើយវាក្លាយជាបញ្ហានៅពេលពួកគេមិនអាច។ Microservices ប្តូរការសម្របសម្រួលរវាងមនុស្ស ទៅជាការសម្របសម្រួលរវាងម៉ាស៊ីន ដែលថ្លៃក្នុងការសាងសង់ និងដំណើរការ ប៉ុន្តែអាចពង្រីកតាមចំនួនក្រុម។ ពេលវេលាត្រឹមត្រូវសម្រាប់ការបំបែក គឺនៅពេលការប្តូរនោះសមនឹងតម្លៃរបស់វា ហើយនោះជាអ្វីដែលអ្នកអាចវាស់វែងបាន ជាជាងស្មាន។

## When Not To Use

ការប្រៀបធៀបនេះគឺជាកែវយឹតខុស នៅពេល៖

- **បញ្ហាពិតគឺគុណភាពកូដ** នៅក្នុង modules។ ទម្រង់ទាំងពីរមិនអាចជួសជុលវាបានទេ។
- **ការ deploy យឺត ព្រោះ pipeline យឺត។** ជួសជុល pipeline។
- **មានក្រុមតែមួយ។** ស្វ័យភាពរបស់ក្រុម ដែលជាអត្ថប្រយោជន៍ចម្បងរបស់ microservices មិនពាក់ព័ន្ធទេ។

## Common Mistakes

- **បំបែកតាមទំហំ** («monolith ធំពេក») ជាជាងបំបែកតាមការជាប់ទាក់ទង និងភាពជាម្ចាស់។
- **ការសរសេរឡើងវិញទាំងស្រុងក្នុងពេលតែមួយ** ទៅជា microservices ដែលបញ្ឈប់ការងារលើមុខងារថ្មីរាប់ខែ ហើយជាធម្មតាខកខានឥរិយាបថដែលប្រព័ន្ធចាស់មាន។
- **ដកចេញ services តែរក្សា database រួមតែមួយ** ដែលរក្សាការជាប់ទាក់ទងទាំងអស់ ហើយបន្ថែម network មួយទៀត។
- **មិនដែលលុបផ្លូវចាស់** បន្ទាប់ពីការដកចេញ ដូច្នេះការអនុវត្តពីរត្រូវបានថែទាំ។
- **មិនអើពើការចំណាយលើ platform៖** CI/CD, observability និង on-call សម្រាប់ service ថ្មីនីមួយៗ។
