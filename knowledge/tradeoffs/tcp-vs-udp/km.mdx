## Context

នៅកម្រិត Transport Layer នៃអ៊ីនធឺណិត (Layer 4) ចរាចរណ៍ទិន្នន័យស្ទើរតែទាំងអស់ត្រូវបានគ្រប់គ្រងដោយ Protocols គ្រឹះពីរ៖
1. **TCP (Transmission Control Protocol)៖** ផ្តោតលើការតភ្ជាប់ (Connection-oriented)។ វាបង្កើតការតភ្ជាប់តាមរយៈ 3-Way Handshake (`SYN`, `SYN-ACK`, `ACK`), ធានាថារាល់ Byte ទាំងអស់ទៅដល់គោលដៅដោយមិនបាត់បង់ និងមានលំដាប់លំដោយរៀបរយ ព្រមទាំងការពារកុំឱ្យស្ទះ Network តាមរយៈ Flow Control និង Congestion Windows។
2. **UDP (User Datagram Protocol)៖** គ្មានការតភ្ជាប់ (Connectionless)។ វាបញ្ជូនកញ្ចប់ទិន្នន័យឯករាជ្យ ("Datagrams") ទៅកាន់ Port គោលដៅដោយមិនចាំបាច់ Handshake, មិនធានាថាទៅដល់ ឬអត់, និងមិនមានការបញ្ជូនសារឡើងវិញឡើយ។ បើ Router ណាមួយកកស្ទះទម្លាក់កញ្ចប់ទិន្នន័យចោល ទិន្នន័យនោះនឹងបាត់បង់ជារៀងរហូត។
3. **QUIC (HTTP/3)៖** បង្កើតឡើងនៅលើ UDP ប៉ុន្តែបន្ថែមភាពជឿជាក់ និង Congestion Control ដូច TCP ដោយគ្មានបញ្ហា Head-of-Line Blocking ឡើយ ព្រមទាំងគាំទ្រ 0-RTT Handshake និងការប្តូរបណ្តាញពី Wi-Fi ទៅ 4G/5G ដោយមិនដាច់ការតភ្ជាប់។

ការជ្រើសរើសខុស នឹងធ្វើឱ្យការផ្សាយវីដេអូ ឬសំឡេងត្រូវគាំងកន្ត្រាក់ៗ (ករណី TCP បញ្ជូនកញ្ចប់ទិន្នន័យចាស់ឡើងវិញ) ឬធ្វើឱ្យខូចទិន្នន័យហិរញ្ញវត្ថុដោយស្ងាត់ៗ (ករណីប្រើ UDP លើការផ្ទេរលុយ)។

## Symptoms

- **TCP Head-of-Line Blocking៖** ហ្គេមអនឡាញ ឬការហៅទូរស័ព្ទផ្ទាល់ត្រូវគាំង ៣០០ ms រាល់ពេលមានកញ្ចប់ទិន្នន័យតែមួយធ្លាក់បាត់លើសេវាទូរស័ព្ទ ព្រោះ TCP ផ្អាកការបញ្ជូនទិន្នន័យទាំងអស់ដើម្បីរង់ចាំកញ្ចប់ទិន្នន័យដែលបាត់នោះ Re-transmit មកដល់សិន។
- **ការបាត់បង់ទិន្នន័យលើ UDP៖** កម្មវិធីព្យាយាមផ្ទេរប្រតិបត្តិការហិរញ្ញវត្ថុ ឬឯកសារ Binary តាម UDP សុទ្ធ; កញ្ចប់ទិន្នន័យមកដល់ខុសលំដាប់លំដោយ ឬបាត់បង់តាមផ្លូវ ដែលធ្វើឱ្យទិន្នន័យខូចខាតទាំងស្រុង។
- **ការពន្យារពេលដោយសារ Handshake៖** ទូរស័ព្ទដៃដែលប្រើសេវាខ្សោយ (Latency ១៥០ ms) ត្រូវចំណាយពេល ៤៥០ ms គ្រាន់តែដើម្បីធ្វើ TCP និង TLS Handshake មុនពេលអាចផ្ញើទិន្នន័យ HTTP បានមួយ Byte។

## Diagnose

1. **វាយតម្លៃកម្រិតអត់ធ្មត់នឹងការបាត់បង់កញ្ចប់ទិន្នន័យ (Packet Loss)៖** ប្រសិនបើបាត់បង់ ១% នៃកញ្ចប់ទិន្នន័យ តើកម្មវិធីខូចទាំងស្រុង (ឯកសារខូច, API Error) ឬគ្រាន់តែមានស្នាមរអាក់រអួលសំឡេងបន្តិចបន្តួច?
2. **វាស់វែងកម្រិតកំណត់នៃ Latency៖** តើការងាររបស់អ្នកទាមទារ Latency ក្រោម 50 ms (ហ្គេមប្រយុទ្ធ, WebRTC Video Call, សំឡេងផ្ទាល់) ឬតើ ២០០ ms គឺជាកម្រិតដែលអាចទទួលយកបាន?
3. **ពិនិត្យមើលបរិយាកាស Network៖** តើអ្នកប្រើប្រាស់របស់អ្នកស្ថិតនៅលើបណ្តាញទូរស័ព្ទមិននឹងនរ (ក្នុងរថភ្លើងក្រោមដី, ការប្តូរបង្គោលអង់តែន) ដែលងាយនឹងជ្រុះបាត់កញ្ចប់ទិន្នន័យមែនទេ?
4. **ពិនិត្យប្រេកង់នៃការតភ្ជាប់៖** តើ Client ផ្ញើសំណើតូចៗម្តងម្កាល (ដូចជា DNS Query) ដែលការធ្វើ 3-Way TCP Handshake នឹងបង្កើនរយៈពេលទ្វេដងមែនទេ?

## Options

1. **Standard TCP (HTTP/1.1 & HTTP/2)៖** ភាពជឿជាក់រឹងមាំ, ទិន្នន័យមានលំដាប់រៀបរយ, គាំទ្រដោយ Hardware គ្រប់កន្លែង។ (ជួបបញ្ហា Handshake Latency និង Head-of-line Blocking)។
2. **Raw UDP៖** គ្មានការ Handshake, Header តូចត្រឹមតែ ៨ Bytes, បាញ់ចេញភ្លាម។ (គ្មាន Congestion Control, អាចបាត់បង់ ឬមកដល់ខុសលំដាប់)។
3. **WebRTC (UDP + SRTP / SCTP)៖** ការបញ្ជូនសំឡេង វីដេអូ និងទិន្នន័យផ្ទាល់រវាង Peer-to-Peer ជាមួយ Encryption និង Jitter Buffers ដែលមានស្រាប់។
4. **QUIC / HTTP/3៖** ការបញ្ជូនទិន្នន័យលើ UDP ដែលមាន TLS 1.3 ជាប់ជាមួយ ដោយលុបបំបាត់ Head-of-line Blocking ឆ្លងកាត់ Streams ផ្សេងៗគ្នា។

## Trade-offs

| លក្ខណៈវិនិច្ឆ័យ | TCP | UDP | QUIC (HTTP/3) |
| :--- | :--- | :--- | :--- |
| **ភាពជឿជាក់ និងលំដាប់ទិន្នន័យ** | **ធានា ១០០% (គ្មានការបាត់បង់)** | គ្មាន (តាមយថាកម្ម) | **ធានាលើ Stream នីមួយៗ** |
| **ការបង្កើតការតភ្ជាប់** | ១ RTT (3-way Handshake) | **០ RTT (គ្មានការតភ្ជាប់)** | **០ ដល់ ១ RTT (មាន TLS 1.3 ស្រាប់)** |
| **Head-of-Line Blocking** | ខ្ពស់ (បាត់កញ្ចប់មួយទប់ទាំងអស់) | **គ្មានទាល់តែសោះ** | **គ្មានរវាង Streams ផ្សេងគ្នា** |
| **ទំហំ Header Overhead** | ២០ ដល់ ៦០ Bytes ក្នុង ១ កញ្ចប់ | **៨ Bytes** | ប្រែប្រួល (តូចច្រឡឹង) |
| **Congestion Control** | មានស្រាប់ (BBR, CUBIC) | គ្មាន (ត្រូវសរសេរក្នុង App) | មានស្រាប់ (BBR ទំនើប) |
| **ភាពឆបគ្នាជាមួយ Firewall** | **គ្រប់ទីកន្លែង (មិនដែលត្រូវគេបិទ)** | ភាគច្រើនបើក | ពេលខ្លះត្រូវគេ Block UDP Port 443 |

## Decision

- **ជ្រើសរើស TCP សម្រាប់៖**
  - Web REST/JSON APIs, GraphQL, gRPC លើ HTTP/2។
  - Database Client Connections (PostgreSQL, Redis, MySQL)។
  - ការផ្ទេរឯកសារ, ការទាញយកកម្មវិធី, Email (SMTP/IMAP), និង SSH។
  - រាល់ប្រព័ន្ធណាដែលការបាត់បង់ Byte សូម្បីតែមួយ ធ្វើឱ្យទិន្នន័យខូចខាតទាំងស្រុង។
- **ជ្រើសរើស UDP សម្រាប់៖**
  - ហ្គេមអនឡាញដែលទាមទារការ Sync ទីតាំងតួអង្គក្នុងពេលជាក់ស្តែង។
  - Voice-over-IP (VoIP), ការផ្សាយផ្ទាល់វីដេអូ, និង Video Conference (WebRTC)។
  - ប្រព័ន្ធបញ្ជូន Telemetry និង Metrics ល្បឿនលឿន (StatsD, Syslog)។
  - ការសាកសួរឈ្មោះដែន DNS (ល្បឿនសំខាន់បំផុត បើបាត់គ្រាន់តែសួរម្តងទៀត)។
- **ដំឡើងទៅកាន់ QUIC / HTTP/3 សម្រាប់៖**
  - Web និង Mobile Applications ទំនើបដែលមានអ្នកប្រើប្រាស់ទូទាំងពិភពលោកលើបណ្តាញទូរស័ព្ទ ដែលជួយកុំឱ្យដាច់ការតភ្ជាប់ពេលប្តូរពី Wi-Fi ទៅ 5G។

## Implementation

### 1. Reliable TCP Server ក្នុង Node.js៖

```typescript
import net from 'net';

// TCP Server: ធានាថារាល់ Byte ទាំងអស់មកដល់តាមលំដាប់លំដោយឥតខ្ចោះ
const tcpServer = net.createServer((socket) => {
  console.log(`[TCP] Client បានភ្ជាប់៖ ${socket.remoteAddress}:${socket.remotePort}`);

  socket.on('data', (buffer) => {
    console.log(`[TCP] ទទួលបានទិន្នន័យតាមលំដាប់ (${buffer.length} bytes)`);
    // ឆ្លើយតបត្រឡប់ទៅវិញដោយភាពជឿជាក់
    socket.write(buffer);
  });

  socket.on('error', (err) => console.error('[TCP] Error:', err.message));
});

tcpServer.listen(9000, () => console.log('TCP Server កំពុងដំណើរការលើ Port 9000'));
```

### 2. UDP (Datagram) Server ល្បឿនលឿនសម្រាប់ប្រមូល Metrics៖

```typescript
import dgram from 'dgram';

// UDP Socket: លឿនបំផុត គ្មាន Handshake បាញ់ហើយចប់ (< 0.1 ms)
const udpSocket = dgram.createSocket('udp4');

udpSocket.on('message', (msg, rinfo) => {
  // ដំណើរការ Metrics ភ្លាមៗដោយគ្មានការតភ្ជាប់ស្មុគស្មាញ
  const metricString = msg.toString();
  // ទម្រង់ StatsD: "api.requests:1|c"
  recordMetric(metricString);
});

udpSocket.bind(8125, () => console.log('UDP StatsD Server កំពុងដំណើរការលើ Port 8125'));

function recordMetric(data: string) {
  // កត់ត្រា Metric ដោយមិនបាច់ឆ្លើយតប Ack ឡើយ (គ្មាន Network Return Trip!)
}
```

## Verification

1. **ការធ្វើតេស្តទម្លាក់កញ្ចប់ទិន្នន័យ (Packet Drop Simulation)៖** ប្រើប្រាស់ `tc` លើ Linux ដើម្បីបង្កើត 5% Packet Loss៖ `tc qdisc add dev eth0 root netem loss 5%`។ ផ្ទៀងផ្ទាត់ថា Latency របស់ TCP កើនឡើងខ្ពស់ដោយសារការ Re-transmit ខណៈដែល Latency របស់ UDP នៅតែថេរដដែល។
2. **ការវាស់ស្ទង់រយៈពេល Handshake៖** ប្រៀបធៀប Time-to-first-byte រវាង TCP+TLS 1.2 (៣ RTTs) ធៀបនឹង QUIC (១ RTT ពេល Cold, ០ RTT ពេលបន្ត)។ QUIC ត្រូវតែបង្កើតការតភ្ជាប់លឿនជាង ៦០% លើបណ្តាញទូរស័ព្ទ។
3. **ការធ្វើតេស្តប្តូរបណ្តាញពី Wi-Fi ទៅ 4G/5G៖** បញ្ជូនទិន្នន័យតាម HTTP/3 QUIC លើទូរស័ព្ទដៃ រួចបិទ Wi-Fi។ ផ្ទៀងផ្ទាត់ថាការបញ្ជូនទិន្នន័យនៅតែបន្តទៅមុខរលូនដោយមិនដាច់ ឬតម្រូវឱ្យភ្ជាប់ឡើងវិញឡើយ។

## Why

នៅកម្រិត Hardware រាល់ Routers និង Switches ទាំងអស់ដំណើរការដោយការបញ្ជូនកញ្ចប់ទិន្នន័យឆ្លងកាត់ខ្សែរូបវន្ត។ នៅពេល Buffer ពេញ Router គ្រាន់តែទម្លាក់កញ្ចប់ទិន្នន័យចោលលើដីប៉ុណ្ណោះ។
- **TCP បង្ខំឱ្យពិភពឌីជីថលក្លែងបន្លំភាពល្អឥតខ្ចោះ៖** វាផ្អាកពេលវេលា, តាមដានលំដាប់លេខ, និងស្នើសុំទិន្នន័យដែលបាត់ឡើងវិញរហូតទាល់តែគ្រប់គ្រាន់ ១០០%។
- **UDP ទទួលយកការពិតជាក់ស្តែង៖** វាផ្តល់អាទិភាពដល់បច្ចុប្បន្នភាពជាងភាពល្អឥតខ្ចោះនៃអតីតកាល។ ក្នុងការសន្ទនារបស់មនុស្ស ប្រយោគដែលនិយាយកាលពី ៥០០ ms មុនគឺគ្មានតម្លៃអ្វីទាំងអស់បើធៀបនឹងប្រយោគដែលកំពុងនិយាយនៅពេលនេះ។

ការយល់ដឹងពីចំណុចនេះ ជួយឱ្យអ្នកជ្រើសរើស Transport Protocol ឱ្យត្រូវគ្នានឹងលក្ខណៈពេលវេលាពិតនៃទិន្នន័យរបស់អ្នក។

## When Not To Use

- **UDP សម្រាប់បញ្ជីគណនេយ្យហិរញ្ញវត្ថុ៖** ប្រសិនបើកញ្ចប់ទិន្នន័យដែលផ្ទុកទឹកប្រាក់ `$10,000` ធ្លាក់បាត់ សៀវភៅបញ្ជីធនាគារនឹងត្រូវខូចខាតជាអចិន្ត្រៃយ៍។
- **TCP សម្រាប់ហ្គេមបាញ់គ្នាកម្រិតពិភពលោក៖** កញ្ចប់ទិន្នន័យដែលបាត់តែមួយ នឹងធ្វើឱ្យតួអង្គទាំងអស់ត្រូវកកស្ងៀមនៅលើកញ្ចក់អេក្រង់អំឡុងពេលរង់ចាំ TCP Re-transmit។

## Common Mistakes

- **ព្យាយាមបង្កើត TCP ឡើងវិញលើ UDP ដោយខ្លួនឯង៖** ការសរសេរកូដ Ack និង Re-transmit ដោយដៃលើ UDP ដោយគ្មាន Congestion Control ត្រឹមត្រូវ នឹងធ្វើឱ្យស្ទះ Network ទាំងស្រុង។ ត្រូវប្រើ QUIC ឬ WebRTC ជំនួសវិញ។
- **ភ្លេចគិតពីរឿង Corporate Firewall បិទ UDP៖** សន្មតថា UDP Port 443 (QUIC) តែងតែបើកចំហរ។ ក្រុមហ៊ុនជាច្រើនបិទចរាចរណ៍ UDP ទាំងអស់។ ត្រូវរៀបចំប្រព័ន្ធឱ្យចេះ Fallback ទៅកាន់ TCP/HTTPS ដោយស្វ័យប្រវត្តិ។
- **ផ្ញើកញ្ចប់ទិន្នន័យធំពេកលើ UDP៖** ការផ្ញើសារដែលធំជាងកម្រិត MTU របស់បណ្តាញ (ជាទូទៅ ១,៥០០ Bytes) បង្ខំឱ្យមាន IP-level Fragmentation។ បើបាត់បង់បំណែកតែមួយ កញ្ចប់ទិន្នន័យ UDP ទាំងមូលនឹងត្រូវបោះចោល។ ត្រូវរក្សាទុក UDP Payload ឱ្យនៅក្រោម ១,៤០០ Bytes ជានិច្ច។
